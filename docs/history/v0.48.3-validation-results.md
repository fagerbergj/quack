## Finding 1 — quack cannot export to Langfuse's OTLP endpoint (blocks phase 7)

The plan's prerequisite — "point `observability.otel.otlp_endpoint` at Langfuse" —
does not work as written.

`signalURL` (`internal/otelobs/provider.go:61-71`) returns the endpoint unchanged
when it already contains a path, instead of appending `/v1/traces`, `/v1/metrics`
or `/v1/logs`. Langfuse's OTLP base is `/api/public/otel`, which has a path. Every
export then posts to that base and gets a 404:

```
traces export: failed to send to http://…:3008/api/public/otel: 404 Not Found
failed to upload metrics: … 404 Not Found
```

The endpoint itself is fine — a direct POST to `/api/public/otel/v1/traces`
returns 200.

Workaround used here: set `otlp_endpoint` to the full
`…/api/public/otel/v1/traces`. Traces then export cleanly (0 failures), but
**metrics still 404**, because they need `/v1/metrics` on the same base. That is
why phase 7 could not be validated at all.

Two ways out: require an OTel collector in front of Langfuse (and say so in the
plan's prerequisites), or make `signalURL` append the signal path even when a path
is present.

## Finding 2 — one run produces MANY traces, not one (contradicts phase 4)

Phase 4 states: *"it is deliberately trace-level, not per-node. Every node on a
run links to the same trace. That is expected."*

Observed otherwise. A single two-node chat (`48e9470e-0e40-4c5e-86e9-63d383faa134`)
produced **at least 5 distinct trace ids**, e.g.

- `0d36a5a5…` — `gen_ai.agent.name=web-researcher`, `quack.node=select`
- `8476806d…` — `gen_ai.agent.name=judge`, `quack.node=channel`

Both carry the same `sessionId` / `gen_ai.conversation.id`, so the run is still
correlatable — but by **session, not by trace**. A single per-run trace link
therefore cannot open "the run"; from one node it opens a trace that does not
contain the other node's work.

Worth confirming whether this is intended (a per-node A2A server plausibly starts
a fresh trace root) and, if so, rewording phase 4 and the "known and expected"
list. As written, a tester following phase 4 step 3 will report a bug.

## Phase 1 — default posture unchanged: PASS

Deployed with no config change beyond enabling OTel.

- Generations show model, token counts and cost, as on 0.48.2.
- `input: null` and `output: null`. **Content capture is off by default** — the
  stop-the-release gate holds.
- No `quack.*` span is typed as a GENERATION; `quack.run` is a plain SPAN.

## Phase 3 — the central bet: PASS

Trivial single-model-call question, run on both versions.

| | 0.48.2 baseline | 0.48.3 |
|---|---|---|
| trace | `a175b300…` | `96312a6c…` |
| observations | 4 | 4 |
| **GENERATIONs** | **1** | **1** |
| **totalCost** | **0.0000024** | **0.0000024** |
| input / output | null / null | null / null |

Exactly one GENERATION per model call, not two. Cost is **identical**, not
doubled. The design bet holds.

Also observable, and the only diff between the two: 0.48.3 adds
`gen_ai.conversation.id` and populates Langfuse's `sessionId` with the chat id.
That is the continuity feature working.

## The plan's one genuinely unverified claim: ANSWERED

`gen_ai.agent.name` **is** present on the generation span
(`web-researcher`, `judge`) and it changed **nothing** about how Langfuse treats
the observation:

- type is still `GENERATION`
- `providedModelName` still resolves (`qwen3.8-27b`, `gemma4-26b-a4b`)
- `internalModelId` and `usagePricingTierId` still resolve, cost still attributed

No need to rename it to `quack.agent`.

## Phase 6 — node correlation: PASS

Generations carry `quack.node` (`select`, `channel`) and `gen_ai.agent.name`
(`web-researcher`, `judge`), so a run can be filtered to a single node. Node ids
here were slug-shaped, so the export guard was not exercised.

## Not run, and why

- **Phase 2** needs the UI and a forced judge failure at concurrency capacity.
  Note 2a's setup gets harder once quack#1029 lands: a steer will no longer force
  a full round re-run, so the `-s{N}` suffix fires less often. Worth a note in the
  plan so "couldn't reproduce" is not read as a regression.
- **Phase 4** needs `trace_url_template` plus the UI; see finding 2 first.
- **Phase 5** (content capture) — deliberately not enabled; next in line.
- **Phase 7** blocked by finding 1.
- **Phase 8** (rollback) not attempted.

*"A delivered steer never appears in `gen_ai.input.messages` (blocked on #1029)"*
