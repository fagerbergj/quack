# extensions

The extension SDK for quack, plus quack's first-party extensions. Until 2026-10 these lived in `github.com/fagerbergj/quack-extensions` (archived); their history before the move is there. Full design: [issue #275](https://github.com/fagerbergj/quack/issues/275#issuecomment-5245275574). How to work on one, ship a plugin change, or add an extension: [docs/extensions/dev-loop.md](../docs/extensions/dev-loop.md).

## The invariant

**An extension reaches quack only through the SDK.** The SDK is self-contained (chi, slog, adk's `tool.Tool`); extensions import only the SDK, and quack imports the SDK for the seam types and each extension package once, as a blank import in `internal/serve/extensions_registry.go`, for registration. [`boundary_test.go`](boundary_test.go) enforces both directions. This is what lets an extension be written outside this repository against the SDK alone, compile into quack's binary, and still be enabled or left dormant per deployment by config alone.

A consequence: extensions shape a run only at dispatch time (`DispatchRequest`'s `Chat`/`Ask`/`Run`/`Delivery` groups). There are no agent-loop hooks - enforcement stays gate-owned inside quack.

A chat runs one run at a time. `Host.Dispatch` onto a chat whose run is still live dispatches nothing and returns an error wrapping `sdk.ErrRunInFlight`; treat it as busy, not as a host failure, and retry from that chat's `RunEnded` if the ask must not be lost.

A run whose node the user pauses ends with `sdk.RunPaused`, which is not final: keep whatever the run holds, because resuming the node delivers a second `RunEnded` with the real outcome.

## SDK versioning

`sdk`'s exported identifiers are the contract between quack and every extension; the doc comments in [`sdk/sdk.go`](sdk/sdk.go) describe the current surface, and the `sdk/vX.Y.Z` tags from the old repository carry its history. Optional capabilities are interfaces quack detects by type assertion, and `Host` func fields may be nil on an older host, so callers nil-check them.

`sdk/` is its own module, `github.com/fagerbergj/quack/extensions/sdk`, so an outside extension can depend on it alone; quack's `go.mod` replaces it with `./extensions/sdk`, so an SDK change and its callers land in one commit. A release for outside authors is an `extensions/sdk/vX.Y.Z` tag. It stays on 0.x until quack reaches 1.0: treat every minor bump as potentially breaking and pin exact versions.

## Layout

```text
sdk/         github.com/fagerbergj/quack/extensions/sdk (own module) - the Extension API
android/     agent tools that drive an Android emulator over the adb host protocol
browser/     agent tools that drive a Chromium over CDP
github/      GitHub App integration and its code-agent plugin
noop/        proves the loop end to end (quack's e2e test fixture)
remarkable/  rmfakecloud document browser -> document-ingest, and that workflow's plugin
sleeper/     Sleeper fantasy-football tools, page and plugin
usage/       in-app Prometheus usage dashboard (inbound-only) and its manifest
```

Every directory but `sdk/` is a package of quack's own module, `github.com/fagerbergj/quack/extensions/<name>`, built and tested with the rest of quack.

## How quack consumes this

Each extension package registers itself via `sdk.Register` from `init()`, and `internal/serve/extensions_registry.go` blank-imports it. Compiled but unconfigured is dormant; configured but not compiled is a loud startup error. Deployments enable and configure extensions through `extensions:` blocks in `quack.yaml`, which quack hands each extension's `Factory` as opaque config bytes.

A module can also ship a declarative plugin (agents, skills, workflows) under `<name>/plugin/`. quack fetches it through its plugin registry as `github:fagerbergj/quack@plugin/<name>/vX.Y.Z#extensions/<name>/plugin`, so a plugin change ships with a `plugin/<name>/vX.Y.Z` tag and a seed bump rather than an image; see [sleeper/README.md](sleeper/README.md#plugin).

## Out of process

Setting `exec: <binary>` in an `extensions.<name>` block runs that extension as a child process instead of calling its compiled-in factory; dropping the key puts it back in-process. The binary's `main` is one call to [`extproc.Main(name, needs...)`](sdk/extproc/serve.go) (see [usage/cmd/quack-ext-usage](usage/cmd/quack-ext-usage/main.go)), where `needs` names the optional `Host` callbacks the extension cannot run without (see [github/cmd/quack-ext-github](github/cmd/quack-ext-github/main.go)). The image ships `/quack-ext-usage`, `/quack-ext-remarkable`, `/quack-ext-sleeper` and `/quack-ext-github`.

### Releasing an extension without a quack release

`exec: release` runs the binary published with the extension's pinned plugin release instead of the image's: tagging `plugin/<name>/vX.Y.Z` publishes `quack-ext-<name>-linux-{amd64,arm64}` and `SHA256SUMS` on that tag's release, and quack runs a downloaded binary only after its checksum matches. After moving the plugin row's pin, `quack extension restart <name>` (`POST /api/v1/extensions/{name}/restart`) starts a child on the new binary and drains the old one, leaving quack and the other extensions running. The steps and limits are in [docs/extensions/dev-loop.md](../docs/extensions/dev-loop.md#releasing-an-extension-without-a-quack-release).

The wire is JSON-RPC 2.0 (protocol 2), one JSON object per line on the child's stdin/stdout, with calls in both directions; each side serves the other's calls concurrently, so a handler may call quack while quack calls it. quack calls `initialize` (config block, data dir, version, public URL, zone, and the optional calls it serves -> UI descriptor, whether the extension is a `RunObserver`, its tool declarations, artifact schemas and decision points, which of `Deliverer`, `GitCredentialSource`, `AssignmentMetaExtension` and `AssignmentFreshnessChecker` it implements, and the routes it mounted on its public router; the child runs the factory and any `Starter.Start` here), then one `http` call per request under `/<name>/`, one `publicHTTP` call per request to a public route, one `tool` call per agent tool call (tool name, args, function call id and the run's `sdk.CallInfo` -> the result map or the tool's error), and one `deliver`, `gitCredential`, `onAssignment` or `beforeAssignment` call per call into those interfaces, and sends a `runEnded` notification (chat id, outcome, `paused` included) to an observer; one sent while the child is down is lost. quack registers each reported tool as a proxy, so agents name it as they would the compiled-in one, and quack's loader reads the schemas, points and interfaces as it reads an in-process extension's. `deliver` returns the outcomes and the error together, as `Deliver` does; `onAssignment` carries the agent ctx's session id, which github's `OnAssignment` reads. The child's `Host.Dispatch` and each other `Host` callback (`readArtifact`, `writeArtifact`, `chatUser`, `archiveChat`, `updateChatOrigin`, `invalidateSetup`, `classify`, `decide`) are calls into quack; `sdk.ErrRunInFlight` and `sdk.ErrUnknownChat` still satisfy `errors.Is` on the far side, and a `DecideRequest.State` reaches the decision handler as the child encoded it. The wire stays at protocol 2 because each addition is optional: a host that does not list a callback leaves that func nil, as an in-process host without it would, and a child refuses to start against a host that omits a callback named in its `needs`, or the call that carries something it has (`tool` for tools, schemas or points, `publicHTTP` for public routes, `deliver` for a `Deliverer`...). Either side sends a `cancel` notification for a call it abandoned: a client that disconnects cancels its handler's `r.Context()`. quack keeps the session auth on everything under `/<name>/` but the reported public routes, which it registers as the extension did in-process and leaves to verify their own callers (github's webhook checks its HMAC signature in the child). It strips `Authorization` and `Cookie` from both, and answers 502 while the child is down. Request and response bodies are capped at 16MiB: an oversized request gets 413, an oversized response 502. The child logs JSON to stderr, re-emitted in quack's log under `component=ext.<name>` (lines over 64KiB are truncated). quack restarts a crashed child with backoff (100ms doubling to 30s, reset once a child outlives 30s) and stops it on shutdown by closing its stdin, then SIGKILL after 5s. The child gets only PATH, HOME, TMPDIR, TZ, LANG, SSL_CERT_FILE, SSL_CERT_DIR and the HTTP(S)_PROXY/NO_PROXY variables from quack's environment.

Limits: `DeliveryRecoverer` does not cross the wire, so boot recovery skips a child that implements it and `quack ledger recover` builds the compiled-in extension. A child's call into quack runs in a fresh ctx, not the ctx of the quack call its handler serves, so a `Decide` from inside `Deliver` or a tool lacks that call's trace and ledger coords, and a dispatched run does not inherit the handler's trace. Public routes come from the first child at boot, and an unknown path under `/<name>/` asks for session auth before the child's 404. A child's tool gets an `agent.Context` carrying only the call's ctx (its cancel and `CallInfo`) and function call id; session, state, memory and artifact calls panic, which a functiontool returns as the call's error. Tools, schemas and points come from the first child at boot, and a respawned child is assumed to report the same ones. A child's `ReadArtifact`, `WriteArtifact`, `ChatUser`, `ArchiveChat`, `UpdateChatOrigin` and `InvalidateSetup` have no ctx, so their caller cannot abandon them: each returns when quack answers or the link closes. A dispatch is one message under the same line cap as a response, so attachments over about 24MiB in total cost the child its process. Responses are buffered, not streamed, and handlers see an empty `Host` and `RemoteAddr`. The child is not sandboxed the way plugin MCP servers are. Validation still runs the compiled-in factory, so an `exec` extension must also be compiled into quack. A child gets 30s to run its factory and `Start` (the longest in-process `Start`, remarkable's login, allows 30s); one that takes longer fails quack's boot, as a failing in-process `Start` does, and fails each later respawn. Writes to the child hold a lock on a blocking pipe, so a child that stops reading stdin stalls whoever is writing to it, including the run-completion goroutine delivering RunEnded.
